Systematic trading bot

A long-only swing strategy, ported from AmiBroker's AFL to Python on the Interactive Brokers API with AI-assisted tools. The strategy itself comes from published work by Critical Trading. My part is making it run unattended and safely.

The design problem

The machine shouldn't have to be awake at the market open. So the bot runs once before the session and hands the broker everything it needs: market-on-open entries, ATR-based stops and limit-on-close exits, linked so that one exit cancels the other.

Built to fail closed

A guard refuses to trade unless the session is provably a paper account, and it has no off switch. Order and position state lives in SQLite, a test suite pins down the strategy's behaviour, and the bot runs as a Linux daemon woken daily by rtcwake.

  • asyncio
  • ib_async
  • SQLite
  • Backtesting
  • Linux

Mathematics thesis · In progress

Symplectic integrators

Most numerical methods slowly drift away from the physics they simulate. Symplectic integrators preserve the geometric structure of Hamiltonian systems, which is why they behave so well over long simulations.

Supervised by Oscar Cosserat, I'm working from symplectic geometry and Darboux's theorem through Hamiltonian vector fields to Lyapunov stability, and then connecting that theory to computation.

  • Symplectic geometry
  • Hamiltonian mechanics
  • Numerical analysis

July 2026 – Present

Cantoblanco, Madrid

Instituto de Ingeniería del Conocimiento

Predictive Analytics Intern

I work on a Python data platform that collects time series from many external providers, each with its own authentication, formats and units, and turns them into one common model. My work has focused on making it more resilient, easier to extend and more trustworthy.

Resume where it failed

After a network cut, a rate limit or a timeout, downloads used to start again from scratch. I built incremental recovery that checkpoints progress locally and resumes from the exact window that failed, plus structured error logging that records the source, root cause and state of every request. That lays the groundwork for telling recoverable failures from permanent ones and retrying automatically.

One integration model for every provider

Each provider had its own code path, and the system authenticated once per configured entry even when entries shared credentials. I grouped them by provider and credentials with vectorised pandas operations, so each set authenticates once and reuses its session. Available devices are now discovered from the providers' APIs instead of being hard-coded, and a declarative configuration layer replaced the per-provider implementations: adding a provider takes a configuration file, not new code.

Self-service onboarding

Registering a new source meant someone editing configuration files by hand. I built an interactive ipywidgets tool where users enter the details themselves. It checks the credentials, verifies compatibility and runs a test download, explains any problem in plain terms, and registers the source only once everything passes.

Physics-based data quality

I extended the integrations to retrieve technical metadata and built a preliminary theoretical model of the expected values, so readings that are physically impossible, frozen or missing get flagged before they reach downstream models. I also reviewed and tuned the forecasting models.

What it taught me: resilience patterns such as retries, idempotence and checkpointing, and applying SOLID design to messy real-world APIs.
